# B06 — Engine fixture, 12 s (repeatability and cost; no creative winner)

> Status: **specified, not run in this repo** (the research repo measured the original fixture, E01). Brief version 0.1, written 2026-10-02 from BENCHMARK_SUITE_SPEC §3 and the E01 report. Synthetic assets only. Specified; model eval not run (decision default Q4). One language-neutral form with Hebrew + Latin + number text inside the fixture.
> Companion: `critic-brief.md` (not used — no creative judgement), `cheap-first-qa.md`, `timing-ledger.md`.

## 1. Task

**Reuse the E01 fixture exactly** — a 12 s, 1080×1920, 30 fps, 360-frame composition — and render it with a **fixed export** to measure **hash repeatability, setup/render/queue costs and export equivalence**. **No creative winner is inferred** from this brief. It exists so the toolkit can answer: "does a fresh install on this machine reproduce frames, and what does it cost?" (it backs the course's setup gate, exercise E0, and the repeatability check in exercise E3).

## 2. Frozen inputs (generator contract — `fixtures/generators/b06/`, regenerated from a script with a pinned seed)

The E01 fixture content: a **Hebrew headline with a Latin word and a number**, a **Ken Burns** move on a still, a **4 s video** clip, **20 particles** (seeded), **3 captions** (Hebrew), a **music bed and 2 SFX** (script-synthesised, redistributable). Export settings fixed: CPU H.264, CRF 18, 30 fps, single worker, software capture (the E01 profile). `fixture_manifest.json` records every asset hash and licence; the composition is versioned code. Engine, browser, font and ffmpeg versions are **pinned and recorded**.

## 3. What is measured

| Outcome | Check |
|---|---|
| hash repeatability | **360/360 decoded-frame hashes + PCM hash + MP4 SHA-256 identical across ≥ 3 repeat renders on the same pin** (within-engine determinism evidence for that pin only) |
| setup cost | install step time, first-use model/browser downloads, cold vs warm; reported separately (an install is not part of a render) |
| render cost | wall seconds, peak RSS, cold and warm; queue wait; render count |
| export equivalence | only after matching export settings; cross-engine SSIM is **not** creative equivalence and is not a claim here |
| coverage | decoded frames = expected frames; status `PASS` only on full coverage |

**Reference values from the research repo (informational, single passes, one machine):** on one reference machine, HyperFrames 0.8.98: **cold 44.262 s, warm 42.292 and 42.406 s**, peak summed RSS 1.70–1.73 GB, MP4 3,641,148 bytes; an alternative engine (Remotion 4.0.531): cold 54.455 s, warm 43.440 and 43.507 s, 2.09–2.14 GB; **360/360 frame hashes, PCM and MP4 SHA identical across repeats within each engine**; cross-engine SSIM mean 0.9768. The HyperFrames install step took 18.0 s (npm); the other engine's 49.3 s + 10.4 s browser (not a from-zero setup). **Do not extrapolate to a 40 s premium composition.** (src: E01 REPORT; distilled/03 §2.3, 2026-10-01) GPU telemetry and independent authoring were **not** run; NVIDIA, Apple Silicon and Linux numbers are **unmeasured**.

## 4. Run record

As B01 §5 with: pin table (engine, Node, browser, ffmpeg, fonts, OS build), settings hash, cache state (cold/warm), per-repeat hashes, and the `doctor` report. A mismatch of hashes between repeats is `FAIL` with the first differing frame index; a decoder failure is `error`; a missing dependency is `unsupported` — never silent.

## 5. Limits

One fixture, one pin, one machine class. Repeatability on the same pin says nothing about upgrades (a version bump is a new experiment), other OSes or GPU capture. A fast render here does not predict a premium composition's time.
